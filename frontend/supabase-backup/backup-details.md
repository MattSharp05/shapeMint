# ShapeMint Supabase Project Analysis

This document provides a comprehensive analysis of the ShapeMint Supabase project, based on the database schema, roles, and Edge Functions.

## 1. Project Overview

ShapeMint is an AI-powered platform for generating and manufacturing 3D models. Users can create 3D models from text prompts or images using the Meshy API. The platform supports downloading the generated models or ordering physical prints from manufacturing partners like Slant3D. The entire backend is orchestrated using Supabase, including database management, authentication, storage, and serverless functions.

## 2. Database Schema Analysis

The project utilizes several schemas, with the `public` schema containing the core application tables and the `auth` and `storage` schemas providing foundational services.

### Key Tables in the `public` Schema

-   **`profiles` / `users` / `user_profile`**: These tables handle user data.
    -   `profiles`: Appears to be the primary table for user profile information, linked to the main `auth.users` table via a one-to-one relationship. It stores user-specific data like full name, avatar URL, and billing/shipping addresses.
    -   `users` & `user_profile`: The existence of these tables alongside `profiles` suggests potential data model redundancy or a legacy structure. It's recommended to consolidate user data into a single `profiles` table linked to `auth.users`.

-   **`generated_models`**: This is a central table that stores metadata for every 3D model generated by a user.
    -   It links to `auth.users` (`user_id`).
    -   Contains URLs for different model formats (`glb_url`, `obj_url`, `stl_url`).
    -   Tracks the model's `status` (`pending`, `completed`, `failed`) and `thumbnail_status`.

-   **`generation_tasks`**: Tracks the asynchronous tasks for creating 3D models via the Meshy API.
    -   Stores the `task_id` from Meshy, `status`, and the final `model_urls`.
    -   This table is crucial for the polling mechanism that checks for model generation completion.

-   **`orders`**: Manages manufacturing orders placed by users.
    -   Contains details about the order, customer information, and the `slant_order_id` from the manufacturing partner.
    -   The `order_data` column (JSONB) stores the complete order payload sent to the partner.

-   **`manufacturing_quotes`**: Stores quotes received from manufacturing partners.
    -   Linked to a `generated_models` and a `user_id`.
    -   The `quote_details` column (JSONB) holds the pricing and filament information from the provider.

-   **`thumbnail_processing_queue`**: Manages a queue for generating thumbnails for 3D models.
    -   This enables asynchronous thumbnail generation, preventing delays in the main model creation flow.
    -   It includes fields for `status`, `priority`, and `attempts` for robust background processing.

### Custom Types (ENUMs)

The database uses several `ENUM` types to enforce data consistency:
-   `model_status`: `pending`, `processing`, `completed`, `failed`
-   `order_status`: `pending`, `processing`, `shipped`, `completed`, `cancelled`, `failed`
-   `provider_type`: `Slant3D`, `Printify`, `Xometry`
-   `source_type`: `text`, `image`

### Functions and Triggers

-   **`handle_new_user()` function**: This trigger function automatically creates a new record in the `public.profiles` table whenever a new user signs up via Supabase Auth. This is a best practice for separating public user data from sensitive auth data.

## 3. Edge Functions Analysis

The Edge Functions contain the core business logic and integrations with third-party APIs.

-   **`generate-3d-model`**: The primary function for creating 3D models. It takes a user prompt or image, calls the Meshy API, polls for completion, downloads the resulting GLB and OBJ files, uploads them to Supabase Storage, and finally triggers the `obj-to-stl` function.
-   **`obj-to-stl`**: A utility function that converts an OBJ model file into an STL file, which is the standard format for 3D printing. It also intelligently scales the model to a 50mm maximum dimension, preparing it for services like Slant3D.
-   **`refine-model`**: Allows users to refine a previously generated "preview" model from Meshy with more detail or a new texture prompt.
-   **`create-checkout-session`**: Integrates with Stripe to create a secure payment session for users to purchase model downloads or manufacturing orders.
-   **`slant3d-*` Functions**:
    -   `slant3d-quote`: Gets a price estimate from the Slant3D API for printing a model.
    -   `slant3d-order`: Submits a formal order to Slant3D for manufacturing.
    -   `slant3d-filaments` & `slant3d-slicer`: Likely used to get available materials and prepare models for printing.
-   **Thumbnail Generation Functions**:
    -   `generate-thumbnail`: Creates placeholder thumbnail images for models.
    -   `process-thumbnail-queue`: Runs periodically to process models that are pending thumbnail generation.
    -   `cleanup-thumbnails`: A maintenance function to remove unused, auto-generated thumbnail images.
    -   `trigger-thumbnails`: Populates the thumbnail generation queue with models that need thumbnails.
-   **`test-comfyui`**: A function for integrating with a ComfyUI instance, a powerful node-based interface for generative AI workflows. This is likely used for more advanced or custom image-to-3D pipelines.

## 4. Key Workflows

### A. 3D Model Generation Flow

1.  A user submits a text prompt or an image from the frontend.
2.  The `generate-3d-model` Edge Function is invoked.
3.  The function calls the Meshy API (text-to-3D or image-to-3D endpoint).
4.  Meshy returns a `task_id`, which is stored in the `generation_tasks` table.
5.  The function begins polling the Meshy API with the `task_id` to check the generation status.
6.  Once the status is `SUCCEEDED`, the function downloads the GLB and OBJ model files from Meshy.
7.  These files are uploaded to the `3d-models` bucket in Supabase Storage.
8.  The `obj-to-stl` function is called to convert the OBJ file to a scaled STL file, which is also saved to storage.
9.  A new record is created in the `generated_models` table with the public URLs to the GLB, OBJ, and STL files.
10. The `trigger-thumbnails` function is invoked (or a trigger is used) to add the new model to the `thumbnail_processing_queue`.

### B. Manufacturing Order Flow

1.  A user selects a generated model and proceeds to the order page.
2.  The frontend calls the `slant3d-quote` function with the model's STL file URL to get a price.
3.  The user confirms the quote and proceeds to payment.
4.  The `create-checkout-session` function is called to generate a Stripe payment link.
5.  After a successful payment, the frontend calls the `slant3d-order` function.
6.  This function sends the complete order details (including shipping information and the STL file URL) to the Slant3D API.
7.  A new record is created in the `orders` table to track the manufacturing order.

## 5. Authentication and Storage

-   **Authentication**: The project uses the built-in Supabase Auth. The `auth.users` table is the single source of truth for user identities. The `handle_new_user` trigger correctly populates a `profiles` table with public-facing data.
-   **Storage**: Supabase Storage is used extensively. Based on the function code, the primary bucket is `3d-models`, which stores the GLB, OBJ, and STL files for each generated model. A `thumbnails` bucket is also likely used for storing generated preview images.

## 6. Enabled PostgreSQL Extensions

The project leverages several powerful PostgreSQL extensions to enhance its functionality:

-   **`uuid-ossp`**: This is used to generate UUIDs, which serve as the primary keys for most tables, ensuring unique and non-sequential identifiers.
-   **`plpgsql`**: The standard procedural language for PostgreSQL. It's essential for writing the server-side functions and triggers, such as the `handle_new_user` function.
-   **`pg_graphql`**: This extension automatically generates a GraphQL API on top of the existing database schema. The frontend likely uses this for efficient and flexible data fetching, allowing it to request exactly the data it needs in a single query.
-   **`pg_stat_statements`**: A crucial tool for performance monitoring. It tracks planning and execution statistics for all SQL queries, helping to identify and optimize slow or inefficient database operations.
-   **`pgcrypto`**: Provides a suite of cryptographic functions. This can be used to encrypt sensitive data at the column level for an additional layer of security.
-   **`supabase_vault`**: Offers a secure, encrypted key-value store directly within the database. While the Edge Functions appear to use environment variables, the Vault provides a more granular and secure way to manage secrets like third-party API keys.

## 7. Security Recommendations

The Supabase security advisor has identified several issues that require attention. Addressing them will significantly improve the security and robustness of the application.

### High-Priority Errors

1.  **RLS Disabled on `thumbnail_processing_queue`**
    -   **Risk**: **Critical**. The `thumbnail_processing_queue` table is publicly accessible without Row Level Security. This could potentially expose internal processing data and model IDs to unauthorized users.
    -   **Remediation**: Enable Row Level Security on this table immediately. Create policies that restrict access to authorized roles, such as service roles or authenticated users who own the corresponding models.
    -   **Example Policy (Deny Public Access)**:
        ```sql
        -- Enable RLS
        ALTER TABLE public.thumbnail_processing_queue ENABLE ROW LEVEL SECURITY;

        -- Allow service roles to access all rows
        CREATE POLICY "Allow service roles" ON public.thumbnail_processing_queue
        FOR ALL USING (auth.role() = 'service_role');
        ```

2.  **Security Definer View (`order_summary`)**
    -   **Risk**: **High**. The `public.order_summary` view is defined with `SECURITY DEFINER`. This means the view runs with the permissions of the user who created it, not the user querying it. This can lead to unintended data exposure if the creator has elevated privileges.
    -   **Remediation**: Change the view to use `SECURITY INVOKER`, which is the default and recommended setting. This ensures that the querying user's permissions and RLS policies are enforced. If `SECURITY DEFINER` is absolutely necessary, ensure the view owner has the minimum required privileges.
    -   **Remediation Command**:
        ```sql
        ALTER VIEW public.order_summary SET (security_invoker = on);
        ```

### Important Warnings

3.  **Mutable Function Search Path**
    -   **Risk**: **Medium**. Several functions (`handle_new_user`, `update_updated_at_column`, etc.) do not have a fixed `search_path`. A malicious user could potentially alter their session's `search_path` to execute functions in a different schema, leading to privilege escalation.
    -   **Remediation**: Explicitly set the `search_path` at the beginning of each function definition to prevent this.
    -   **Example**:
        ```sql
        CREATE OR REPLACE FUNCTION public.handle_new_user()
        RETURNS trigger
        LANGUAGE plpgsql
        SECURITY DEFINER SET search_path = public
        AS $$
        BEGIN
          -- function body
        END;
        $$;
        ```

4.  **Leaked Password Protection Disabled**
    -   **Risk**: **Medium**. The application does not prevent users from signing up with passwords that are known to have been compromised in data breaches.
    -   **Remediation**: Enable the "Leaked Password Protection" feature in your Supabase project's Auth settings. This is a simple toggle that significantly enhances user account security.

5.  **Insufficient MFA Options**
    -   **Risk**: **Low-Medium**. Not offering robust Multi-Factor Authentication (MFA) options makes user accounts more susceptible to takeover.
    -   **Remediation**: Enable additional MFA methods (like TOTP authenticator apps) in the Supabase Auth settings to give users stronger security options.

## 8. Performance Recommendations

The performance advisor has highlighted several opportunities to optimize the database. Implementing these changes will lead to faster queries, especially as the application scales.

### High-Impact Warnings

1.  **Inefficient Row Level Security (RLS) Policies**
    -   **Issue**: A large number of RLS policies across many tables (e.g., `profiles`, `generated_models`, `orders`) use `auth.uid()` or other `auth` functions directly. This causes the function to be re-evaluated for every single row in a query, leading to significant performance degradation.
    -   **Remediation**: Wrap the `auth` function call in a subquery `(SELECT auth.uid())`. This ensures the function is called only once per query, making the policy much more efficient.
    -   **Example Fix**:
        ```sql
        -- Inefficient Policy
        CREATE POLICY "Users can view their own models" ON public.generated_models
        FOR SELECT USING (auth.uid() = user_id);

        -- Optimized Policy
        CREATE POLICY "Users can view their own models" ON public.generated_models
        FOR SELECT USING ((SELECT auth.uid()) = user_id);
        ```

2.  **Multiple Permissive Policies**
    -   **Issue**: Tables like `generated_models` and `generation_tasks` have multiple `PERMISSIVE` policies for the same role and action (e.g., three different `SELECT` policies for the `authenticated` role). PostgreSQL must evaluate all of these policies for every relevant query, which is redundant and slows down access.
    -   **Remediation**: Consolidate the conditions from multiple policies into a single policy using `OR` logic.
    -   **Example Fix**:
        ```sql
        -- Instead of three separate SELECT policies on generated_models...
        -- Policy A: USING (status = 'completed')
        -- Policy B: USING (auth.uid() = user_id)
        -- Policy C: USING (is_public = true)

        -- Combine them into one:
        CREATE POLICY "Consolidated Select Policy" ON public.generated_models
        FOR SELECT USING (
            (status = 'completed') OR
            ((SELECT auth.uid()) = user_id) OR
            (is_public = true)
        );
        ```

### Informational Recommendations

3.  **Unindexed Foreign Keys**
    -   **Issue**: The foreign key columns on `manufacturing_quotes(model_id)`, `model_likes(model_id)`, and `thumbnail_processing_queue(model_id)` are not indexed. This can lead to slow `JOIN` operations when querying related data.
    -   **Remediation**: Create an index on each of these foreign key columns.
    -   **Remediation Commands**:
        ```sql
        CREATE INDEX idx_manufacturing_quotes_model_id ON public.manufacturing_quotes(model_id);
        CREATE INDEX idx_model_likes_model_id ON public.model_likes(model_id);
        CREATE INDEX idx_thumbnail_processing_queue_model_id ON public.thumbnail_processing_queue(model_id);
        ```

4.  **Unused and Duplicate Indexes**
    -   **Issue**: The advisor has identified numerous indexes that appear to be unused, as well as a duplicate index on the `orders` table (`idx_orders_tracking` and `idx_orders_tracking_numbers`). Unused indexes consume storage and add overhead to write operations (INSERT, UPDATE, DELETE).
    -   **Remediation**:
        -   **Duplicate**: Drop one of the redundant indexes on the `orders` table.
        -   **Unused**: Carefully review the list of unused indexes. Before dropping them, confirm they are not used by any infrequent but important queries (e.g., annual reports, data backfills). If an index is truly unused, drop it to reclaim space and improve write performance.
    -   **Remediation Commands**:
        ```sql
        -- Drop duplicate index
        DROP INDEX IF EXISTS public.idx_orders_tracking_numbers;

        -- Example of dropping an unused index
        DROP INDEX IF EXISTS public.idx_generated_models_status;
        ```
